詳細

背景

HASHST_DEV-4526 で npm run unit が走る状態になった。本チケットから src/utils/common.js の関数に単体テストを追加していく（Phase 1）。Phase 1 は影響の大きさで A〜E の5チケットに分けており、本チケットは A: 金額・数値表示 にあたる。

投資家が目にする金額・口数・利回りの表示に直結し、誤表示は誤認につながるため最優先とする。また toFixed は表示だけでなく、ST購入時の手数料・消費税の計算そのものに使われている（後述）。

前提

  • HASHST_DEV-4526 が完了していること
  • Jest 22 のため test.each は使えない。テーブル駆動は素の forEach で書く（4526 のスモークテストと同じ書き方）
  • 現状の挙動を記録するテスト（characterization test）として書く。仕様か不具合か疑わしい挙動が見つかっても本チケットでは修正せず、テストには現状の挙動をコメント付きで記録し、別チケットに切り出す

確認すべき観点

handleNumber

小数部の処理は四捨五入ではなく、正規表現による切り捨て（例: handleNumber(1.99) → '1'）。そのうえで以下を記録する。

  • precision = 4 のとき、小数2桁・3桁区切りなしの書式（'0.00'）になる（arr[4] / ar2[4]）。他の要素は precision と桁数が揃っており、ここだけ意図と異なる可能性がある。意図した仕様か確認する
  • precision が 5 以上のときは undefined を返す
  • 非常に小さい数・大きい数: 内部で数値を文字列化してから正規表現で切り出すため、0.0000001 は '1e-7' となり、先頭の 1 だけを拾って '1' になると推測される。1e21 以上の大きな数も同様に崩れる可能性がある
  • 数値にならない入力（'abc' など）: parseFloat が NaN になり、マッチ結果 null が Number(null) = 0 になるため '0' が返ると推測される
  • -1 より大きい負の小数（-0.5 を精度 0 で渡す等）: 内部で -0 になる。表示が '0' と '-0' のどちらになるかは numeral の挙動次第のため、実際の結果を記録する

※ 上の「推測される」は、コードを読んだ段階での推測で、実行による確認はしていない。

toFixed（手数料・消費税の計算）

呼び出し元は3箇所ともST購入画面 src/views/Resiger/g2107.vue（ST購入：引落口座と買付口数入力）で、いずれも precision = 0、コメントは「小数部を切り捨てること」。

  • 手数料 = 約定金額 × 手数料率（g2107.vue 401行目・408行目）
  • 消費税 = 手数料 × 消費税率（g2107.vue 417行目）

以下を観点とする。

  • 手数料計算の典型的な組み合わせ（約定金額 × 料率で端数が出るケース）で、期待どおりに切り捨てられること。金額・料率は架空の値を使う
  • 浮動小数点誤差が出る値（0.1 * 3 のような値）でも、1円ずれずに切り捨てられること
  • 数値でない入力は加工されずにそのまま返る（isNaN の分岐）。画面に意図しない値が出ないかの観点で記録する
  • Math.floor を使っているため、負数はゼロ方向ではなく負方向に丸まる（例: -1.235 → -1.24）。手数料・消費税が負になることはないため、現在の使われ方では実害は小さい。挙動の記録にとどめる

その他

  • 0.1 + 0.2 のような浮動小数点誤差が出るケースで math* が正しい値を返すこと
  • 0・負数・文字列の数値・NaN になる入力

作業内容

  • test/unit/specs/utils/ 配下に対象関数の spec を追加する（ファイル分割は common.<関数名>.spec.js を基本とする）
  • 疑わしい挙動が見つかった場合は別チケットを起票し、本チケットにリンクする

完了条件

  • 上記対象関数すべてに spec があり、npm run unit が終了コード 0 で完了する
  • MR のパイプラインで unit_test ジョブが成功している
  • 疑わしい挙動について別チケットが起票されている（見つからなかった場合はその旨を本チケットにコメント）

影響範囲

  • 変更は test/ 配下のみ。src/ 配下の変更なし

本チケットに含めないこと

  • 疑わしい挙動の修正 → 別チケット
  • g2107.vue 側（画面コンポーネント）のテスト → 対象外。本チケットでは toFixed 単体の挙動のみを押さえる
  • 入力チェック・文字変換・日付・メールマスクの関数 → 同階層の B〜E チケット

備考

  • テストのフィクスチャには実在の投資家情報・案件情報（約定金額・手数料率など）を使用せず、架空の値のみを用いる

        結果

        • 対象関数すべてに spec を追加（test/unit/specs/utils/common.<関数名>.spec.js。math 系4関数は common.math.spec.js にまとめた）。src/ の変更なし

        • common.js を一時的に書き換えて（toFixed の切り捨て → 四捨五入など4パターン）、テストがそれぞれ失敗することを確認済み（書き換えは戻している）

        「確認すべき観点」の実行結果

        本文で「推測される」としていた点は、以下のとおり実行で確認した。

        • handleNumber(0.0000001) → '1'（推測どおり）。handleNumber(0.0000005, 2) → '5.00'、handleNumber(1e21) → '1'
        • handleNumber('abc') → '0'（推測どおり）。null / undefined / 空文字も '0'
        • handleNumber(-0.5, 0) → '0'（'-0' にはならない）
        • toFixed: 手数料計算の呼び出し方（toFixed(mathMultiply(金額, 料率), 0)）では、素の JS だと誤差が出る組み合わせ（例: 23,000 × 0.011 = 252.99999999999997）でも正しく '253' になる。mathMultiply を通さずに素の JS の積を渡すと '252' になるため、呼び出し側で mathMultiply を使う前提であることをテストに記録した
        • handleNumber(x, 4) の書式と toFixed の負数の丸め方向は、前回コメントの回答どおり仕様として記録した

        別チケット

        • HASHST_DEV-4546 handleNumber / handleInt が指数表記になる数値を正しく表示できない（関連課題に設定済み）
          • 上記の handleNumber に加え、handleInt(0.0000001) / handleInt(1e21) が文字列の 'NaN' を返すことが新たに分かった
          • 実害が出るのは API が 1e-6 未満の値を返す場合に限られるため、優先度「低」で起票。まず該当する項目があるかの確認から

        記録のみで起票しなかったもの

        API から数値が返る前提では起きないと判断し、テストへの記録にとどめた。

        • 数値にならない文字列（'abc' など）を渡すと、toFixed('') / handNotNumberFormat('abc') / mathAdd('abc', 1) / getInStockStr の比率は例外を投げる。一方 handleNumber / handleInt は '0'、convertNumber / transferNumberForHM は数値の 0 を返し、関数ごとに扱いが揃っていない
        • getInStockStr は当初募集で比率が残っていて残口数が 0 のとき「申込受付中」を返す（データ不整合時の挙動）
