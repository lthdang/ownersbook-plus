# Contents

# 1\. Introduction

## 1.1 Purpose

This document defines the screen change requirements for the customer-facing sites (the trading site and the account opening application site) needed so that OwnersBook+ can handle digital securities (security tokens, "ST") under the beneficiary certificate issuing trust ("JS"; 受益証券発行信託) scheme.

Within the project plan scope "Customer sites and reports," this document covers the screens. Reports are covered in the separate volume "Requirements Definition (Statutory Ledgers)."

## 1.2 Background

The current OwnersBook+ system is **built only for the GK-TK scheme (a godo kaisha combined with a tokumei kumiai, i.e., a Japanese LLC plus a silent partnership)**. Under GK-TK, investors hold silent partnership interests in the LLC (legally "electronically recorded transferable rights" / 電子記録移転権利; Paragraph 2 securities).

Under the JS scheme, investors hold trust beneficial interests (legally "electronically recorded transferable securities-representing rights, etc." / 電子記録移転有価証券表示権利等; Paragraph 1 securities). The type of contract, the parties involved, tax treatment, and the documents delivered all change, so **the current system cannot handle JS-scheme STs as is**.

Therefore, based on the requirement specifications from LSEC (Loadstar Securities), we will enable JS-scheme STs while keeping the GK-TK scheme.

### Examples showing the current screens assume GK-TK

- G2-100 (ST purchase: document confirmation) has a "Review and conclude the silent partnership agreement" button.
- The notes in G2-101 (ST purchase: questionnaire) say "return of contributions to silent partners" and "obtain a certified date on the issuer's consent to transfer at a notary office." Neither applies to JS.
- The link in I2-100 (transaction history) is hard-coded as "Tax Return Support document (silent partnership funds)."
- I2-400 (Tax Return Support document) aggregates only two categories, "miscellaneous income / capital gains," and the redemption breakdown uses "contribution / acquisition cost."

# 3\. Approach

Based on Screen Change List v2 (all 76 items across 12 Figma files, checked against the app-vuejs implementation), we take the following approach:

- **Hold scheme differences in data, not hard-coded in screens.** Many screens already fetch documents, notes, insider company lists, and notice tags from APIs or masters. 30 of the 76 items need 0 person-days of screen work and can be absorbed on the API/master side.
- **Manage tax rates, income categories, and terminology through parameters and a glossary.** Remove hard-coded rates such as 20.42%.
- **Do not change TK-type display or behavior.** Confirm no impact on existing customers through regression testing.
- **The largest change is the Tax Return Support document (I2-400).** The 7 related items take 25.5–42 person-days, about 40–50% of the trading site total. Its structure (combine TK and JS in one document or split them) must be decided first.

# 5\. Non-functional Requirements

| **Category**             | **Requirement**                                                                                                                                                                                                                                           |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Maintainability          | Manage scheme-dependent branching, text, tax rates, and documents through masters, APIs, and the glossary; do not hard-code them in screen code. Reflects lessons from the 2024 voluntary partnership (NK) project, which became a pile of one-off fixes. |
| Compatibility            | Do not change TK-type display or behavior. Include major TK scenarios (purchase, sale, distribution, redemption, Tax Return Support document) in regression testing.                                                                                      |
| Supported environments   | Same as today (PC / smartphone, currently supported browsers).                                                                                                                                                                                            |
| Performance              | Maintain the current level. Tax Return Support display and download should show one customer's one year of data in about the same time as today.                                                                                                          |
| Security / personal data | Follow current standards. Show the Tax Return Support document to individual customers only, not to corporate customers.                                                                                                                                  |
| Regulatory compliance    | Use notes, explanations, and documents reviewed by LSEC's compliance department (risk mitigation in the project plan).                                                                                                                                    |
| Operability              | Adding documents, notice templates, tags, and options should in principle be possible by master changes without a screen release.                                                                                                                         |
| Test environment         | Develop and test in the dedicated JS test environment (AWS).                                                                                                                                                                                              |
